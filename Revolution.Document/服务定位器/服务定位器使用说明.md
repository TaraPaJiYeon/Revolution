# 服务定位器（RevServiceLocator）· 使用说明

> 这份文档只回答一个问题：**我该怎么用它？**
> 读完你能做到：3 分钟把服务装起来 · 知道"全局一份"和"每局一份"该怎么选 · 出错了知道那句报错在说什么 · 知道 6 个最容易白干半天的坑。

配套代码：`Assets\Revolution\Runtime\RevServiceLocator\`（8 个 `.cs` / 702 行 + `README.md`）
真实用法示例（接上 GM 指令）：见《GM 指令使用说明》第八章 —— GM 命令从定位器取业务服务，是最常见的组合形态。

## 〇、它是干什么的（一句话）

**把"我用到的某个能力"和"这个能力具体由谁实现"分开。**

```csharp
// 不用它：底层框架想播声音，就得认识上层的声音类 —— 程序集依赖只能单向，写不通
SoundManager.GetInstance().Play("Play_Box_Appear");        // ✗ 底层反向依赖上层

// 用它：底层只认接口，实现在启动期"注册"进来
services.GetRequired<ISoundService>().Play("Play_Box_Appear");   // ✓ 谁实现都行，能换、能假、能测
```

王者荣耀原版用「静态委托 `SysMgr` + 系统注册表 `CSystemManager` + 世界级容器 `DimensionWorld`」**三套机制**解决同一件事（见 `工作日志\第二月\第6周\2026年9月24日\服务定位器\`）。本框架把它收成**一套**：注册 → 取用 → 作用域 → 释放。

**什么时候用**

- 底层模块要调用上层能力（UI 框架要播声音、动作序列要发奖励、资源系统要报日志）；
- 同一个服务类型在不同场景/不同局面需要**各一份**（一局战斗一份战斗上下文）；
- 你想把业务依赖从框架里赶出去，并且**能在不启游戏的情况下跑单测**。

**什么时候别用**

- 只是"少写一个构造参数" —— 那是过度设计，直接传参更清楚；
- 需要自动解析复杂依赖图（那是 DI 容器的活，且与 IL2CPP 热路径相性差）；
- 进程内只有唯一实现的简单工具类 —— 一个 `static class` 更直接。

## 一、3 分钟跑起来（可粘贴）

### 第 1 步：定义你要用的能力（接口）

```csharp
// 放在底层模块里（谁都能引用它，因为它只是一个接口）
public interface ISoundService
{
    void Play(string eventName);
}

public interface IConfigService
{
    string SoundBankPath { get; }
}
```

### 第 2 步：写实现（业务层）

```csharp
public sealed class SoundService : ISoundService
{
    private IConfigService _config;

    // ★ 构造函数里只初始化自己，不要取别的服务（那是 OnInit 的事）
    public SoundService() { }

    public void Play(string eventName) { /* 真的调你的音频系统 */ }
}

// 需要依赖别人时，实现 RevIServiceInit，在 OnInit 里取
public sealed class SoundServiceWithDeps : ISoundService, RevIServiceInit
{
    private IConfigService _config;

    public void OnInit(RevIServiceLocator services)
        => _config = services.GetRequired<IConfigService>();     // ← 这里取依赖

    public void Play(string eventName) { }
}
```

### 第 3 步：启动期装配（整个游戏只写一处）

```csharp
public static class GameServices
{
    // ★ 只 Build 一次，缓存到 static readonly
    public static readonly RevServiceLocator Root = RevServiceLocator.Create()
        .AddSingleton<ISoundService, SoundServiceWithDeps>()          // 接口 → 实现（零反射，启动期不创建）
        .AddSingleton<IConfigService>(Config.Load())                  // 已有实例（容器不释放它）
        .Build();
}
```

### 第 4 步：运行期取用（一行）

```csharp
var sound = GameServices.Root.GetRequired<ISoundService>();    // 必须有：没注册就报错
sound.Play("Play_Box_Appear");

GameServices.Root.Get<IDebugService>()?.Draw();                // 可选能力：没有就 null
```

### 第 5 步：一局 / 一个场景的边界（作用域）

```csharp
using (var battle = GameServices.Root.CreateScope())
{
    var ctx = battle.GetRequired<ICombatContext>();   // 这一局独有的一份
    battle.Tick(Time.deltaTime);                     // 驱动这一局里实现了 RevITickable 的服务
}   // ← 离开 using：这一局的服务按"逆创建序"释放
```

**没写 `.Build()` 会怎样？** 编译不过 —— `Create()` 返回的是构建器，只有 `Build()` 才给你容器（这样"忘了冻结装配"是编译期问题，不是运行期事故）。

## 二、"我要做 X" 对照表（背下这张表就会用）

| 我想做的 | 写法 |
|---|---|
| 注册"全局一份"的服务 | `.AddSingleton<ISoundService, SoundService>()` |
| 注册一个**已经存在的对象** | `.AddSingleton<IConfigService>(Config.Load())` |
| 注册一个需要构造参数的服务 | `.AddSingleton<ISoundService>(s => new SoundService(s.GetRequired<IConfigService>().SoundBankPath))` |
| 注册"每局一份"的服务 | `.AddScoped<ICombatContext, CombatContext>()` |
| 冻结装配、拿到容器 | `.Build()`（**只能调一次**，调两次会报错） |
| 取一个**必需**的服务 | `services.GetRequired<ISoundService>()` |
| 取一个**可选**的服务 | `services.Get<IDebugService>()?.Draw()` 或 `if (services.TryGet<IDebugService>(out var d)) ...` |
| 开一局/一个场景的边界 | `using (var scope = services.CreateScope()) { ... }` |
| 每帧驱动服务 | `services.Tick(Time.deltaTime)`（只要服务实现了 `RevITickable`） |
| 释放（退出场景 / 关游戏） | `services.Dispose()`（幂等，重复调用没事） |
| 让服务在创建后取依赖 | 服务实现 `RevIServiceInit.OnInit(RevIServiceLocator)` |
| 服务每帧做事 | 服务实现 `RevITickable.OnTick(float)` |
| **单测里替换实现** | 另建一个 `RevServiceLocator.Create()...Build()`，注入假实现（不要动生产那份） |

## 三、四个核心概念（讲透，别跳）

### 3.1 Singleton：整个应用一份

- **第一次被取用时才创建**（启动期不会创建，所以启动不会因为"装了一堆系统"变慢）；
- 根容器（`Root`）和它下面的所有作用域**共享同一个实例**；
- 直到根容器 `Dispose()` 才释放。

> 适合：配置、音频、网络、任务系统、日志 —— 那些"全局只有一个才合理"的东西。

### 3.2 Scoped：每个作用域一份

- 每个 `CreateScope()` 出来的容器**各持一份**（也就是"同一类型多实例"）；
- **第一次被取用时创建**，随作用域 `Dispose()` 释放；
- ★ **在根容器上取 Scoped 服务会直接报错**（这是刻意的：根没有"一轮"的语义，取到全局唯一的一份就是 bug 的起点）。

```csharp
using (var a = Root.CreateScope())
using (var b = Root.CreateScope())
{
    // a 和 b 拿到的 ICombatContext 是两个不同对象 —— 这就是"同类型多实例"
    var ca = a.GetRequired<ICombatContext>();
    var cb = b.GetRequired<ICombatContext>();

    // 而 Singleton 两者是同一个
    ReferenceEquals(a.GetRequired<IClock>(), b.GetRequired<IClock>());   // true
}
```

> 适合：一局战斗、一个场景、一个房间、一次副本 —— "生命周期有明确边界"的东西。

### 3.3 CreateScope：一层的边界，不再嵌套

- 作用域**只能从根容器开**（一层就够）；在作用域上再 `CreateScope()` 会报错并告诉你正确写法；
- 需要"多轮并发"，就开**多个平行作用域**，而不是作用域里套作用域。

> 为什么刻意只做一层：作用域嵌套会让"某个服务到底属于哪一层"变得难以回答 —— 王者的 `DimensionWorld` 就是靠"实例字段数组"做到一层隔离的，这个尺度刚好。

### 3.4 谁创建谁负责释放

| 来源 | 谁释放 | 说明 |
|---|---|---|
| `.AddSingleton<IX, X>()` / 工厂注册 | **容器** | 逆创建序释放（后创建的先放，因为后创建的可能依赖先创建的） |
| `.AddScoped<IX, X>()` / 工厂注册 | **容器** | 作用域 `Dispose()` 时；根 `Dispose()` 会先释放它的所有作用域 |
| `.AddSingleton<IX>(已有实例)` | **你自己** | 容器只持有它、绝不 `Dispose` 它（你要是把宿主对象传进来，容器不该替你销毁） |

## 四、完整演练：底层要播声音（王者的真实动机）

把"底层 UI 框架要播声音，但声音实现在上层"用本框架表达一遍，只用了 3 个文件：

**① 底层（BaseScripts 层，只引用接口）**

```csharp
// 底层模块里：我只知道"有人能播声音"
public interface ISoundService { void Play(string eventName); }

public static class RevSound
{
    public static void PlayUiSound(RevIServiceLocator services, string name)
    {
        // 可选能力：没接声音系统就不播（不是错误）
        services.Get<ISoundService>()?.Play(name);
    }
}
```

**② 上层（实现层，引用底层）**

```csharp
public sealed class WwiseSoundService : ISoundService
{
    public void Play(string eventName) => Wwise.PostEvent(eventName);
}
```

**③ 启动期把它们接上（组合根，整个游戏一处）**

```csharp
public static readonly RevServiceLocator Root = RevServiceLocator.Create()
    .AddSingleton<ISoundService, WwiseSoundService>()
    .Build();
```

**结果是**：底层再也不认识上层；单测里换成 `FakeSoundService`，一行不改就能跑：

```csharp
var test = RevServiceLocator.Create()
    .AddSingleton<ISoundService>(new FakeSoundService())     // 用假的
    .Build();
```

## 五、六个最容易白干半天的坑

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | **注册用接口、取用具体类** | `取不到服务 SoundService` | 取的时候也用接口：`GetRequired<ISoundService>()`（报错信息里会提醒你） |
| 2 | **在根容器上取 Scoped** | `ICombatContext 是 Scoped…不能在根容器上取` | 先 `CreateScope()`，在作用域里取 |
| 3 | **同一个服务注册两处** | `服务 IXxx 已经注册过了（第二次来自 …）` | 装配只留一处（框架刻意不做静默覆盖 —— 那是王者 Dimension 服务的老毛病） |
| 4 | **两个服务在构造/OnInit 里互相取** | `检测到循环依赖：A → B → A` | 构造函数只初始化自己；用 `OnInit` 取依赖，且别互相取 |
| 5 | **忘了把 Build 结果缓存起来** | 每次用都重新 Build（会报"已经 Build 过"或白付装配成本） | 缓存到 `static readonly` 字段 |
| 6 | **到处给"全局静态字段"赋值** | 运行到一半行为变了，排查要翻全工程 | 只有组合根能装配；`Build()` 之后容器是只读的（想改只能改装配代码重启） |

## 六、报错信息怎么读（把真实文案抄给你）

| 你会看到 | 它的意思 | 怎么改 |
|---|---|---|
| `取不到服务 IXxx（没有注册过）。已注册的服务：…` | 没注册，或者名字对不上 | 看"已注册的服务"列表对一下；**注册用接口就要用接口取** |
| `IXxx 是 Scoped（每个作用域一份）服务，不能在根容器上取。请在它所属的边界里开作用域…` | 用法错误（不是"没有"） | `using (var scope = Root.CreateScope()) { scope.GetRequired<IXxx>(); }` |
| `检测到循环依赖：A → B → A` | 两个服务互相等对方先创建 | 把互相取用挪到 `OnInit` 之后，或改成"只取真正需要的那一个" |
| `服务 IXxx 已经注册过了（第二次来自 AddSingleton<IXxx, Xxx>()）` | 重复注册 | 合并到一处（或删掉多余那处） |
| `这个 RevServiceLocator 已经 Dispose 了 —— 容器释放后不能再取服务` | 用了已释放的容器 | 场景卸载前把需要的东西取好；或别在卸载后还持有旧容器 |
| `作用域不再嵌套：请从根容器 CreateScope()` | 在作用域上又开作用域 | 开多个平行作用域 |
| `这个 RevServiceBuilder 已经 Build 过了` | 重复 Build | 只 Build 一次并缓存 |

## 七、怎么验证它在工作（可直接跑的测试思路）

本模块是**纯 C#**（不引用 UnityEngine），所以能放进普通 .NET 工程跑。下面是 5 条关键断言（工程内可以用 NUnit 写成用例）：

```csharp
var root = RevServiceLocator.Create()
    .AddSingleton<IClock, Clock>()
    .AddScoped<ISession, Session>()
    .Build();

// ① 作用域隔离：两个作用域的 Scoped 不是同一个对象
var a = root.CreateScope();
var b = root.CreateScope();
Assert.AreNotSame(a.GetRequired<ISession>(), b.GetRequired<ISession>());

// ② Singleton 共享：根与作用域拿到同一个
Assert.AreSame(root.GetRequired<IClock>(), a.GetRequired<IClock>());

// ③ Scoped 在根上取会抛异常（用法守卫）
Assert.Throws<InvalidOperationException>(() => root.GetRequired<ISession>());

// ④ 逆创建序释放：先创建的会后释放
//    （容器只释放"自己创建的"实例，业务传进来的对象不会被动）

// ⑤ 释放后再取会抛异常，而不是默默给你一个坏对象
a.Dispose();
Assert.Throws<InvalidOperationException>(() => a.GetRequired<ISession>());
```

> 本框架交付时就是靠这类断言验证的：一条 19 连测全部通过（含循环依赖、失败回滚、Tick 只驱动本容器等）。

## 八、一页速查卡（可打印）

**装配（只在一处写）**

- `RevServiceLocator.Create()` → 构建器；`.Build()` → 容器
- `AddSingleton<IX, X>()` / `AddSingleton<IX>(实例)` / `AddSingleton<IX>(s => new X(...))`
- `AddScoped<IX, X>()` / `AddScoped<IX>(s => new X(...))`

**取用**

- `GetRequired<IX>()` 必须有 · `Get<IX>()` 可能有（null） · `TryGet<IX>(out var x)` 要 bool

**边界**

- `CreateScope()` 一局/一个场景一份 · `Tick(dt)` 驱动 `RevITickable` · `Dispose()` 逆序释放（幂等）

**钩子**

- `RevIServiceInit.OnInit(services)`：创建后取依赖（构造函数里不要取）
- `RevITickable.OnTick(dt)`：每帧做事（宿主每帧调 `services.Tick(dt)`）

**三条铁律**

1. 装配只在一处（组合根），`Build()` 之后改不了；
2. `GetRequired` 用于必需依赖（漏注册启动期就炸），`Get` 只用于可选能力；
3. 谁创建谁负责释放：容器释放"工厂创建的服务"，你自己传进来的实例由你释放。

## 九、与王者原版的对照（简表）

| 保留（精华） | 改掉（糟粕） |
|---|---|
| 显式注册 + 组合根唯一前置（运行期只读） | 202 个 `public static` 可变字段（谁都能改，只靠口头纪律） |
| 接口优先、依赖倒置 | Init 抛异常但实例仍留在容器里（半初始化） |
| 幂等注册 | 重复注册静默覆盖（旧实例还不销毁） |
| **零反射**泛型 `new()` 工厂 | 手写 22 分支 switch 工厂 + 枚举扩展仪式 |
| "先入表、再 Init" 不变量 | 全量卸载不摘钩子（与单个卸载不对称） |
| 能力探测式挂载（`RevITickable` 自动进 Tick 列表） | 内部集合外泄（`GetSystems()` 返回可变 List） |
| 逆序卸载 | 未注入返回 null 兜底 → 掩盖错误，调用点常不判空 |
| 作用域隔离（同类型多实例） | World 级服务被挂成全局单例就破坏多实例 |
| `Get` / `TryGet` 三态语义 | 250 字段单文件 + 5 个近义入口（`SafeGet`/`Get`/`ContainSystem`…） |
| — | 容器绑死 MonoBehaviour 单例，无法脱离引擎单测 |
