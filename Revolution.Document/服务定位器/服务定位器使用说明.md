# 服务定位器（RevServices / RevServiceLocator）· 使用说明

> 这份文档只回答一个问题：**我该怎么用它？**
> 读完你能做到：**一行代码注册服务、一行取用、不用了一行注销（释放内存）** · 知道"全局一份"和"每局一份"该怎么选 · 出错了知道那句报错在说什么 · 知道最容易白干半天的坑。

配套代码：`Assets\Revolution\Runtime\RevServiceLocator\`（11 个 `.cs`；你**只需要读 `Facade\RevServices.cs` 这一个**）
真实用法示例（接上 GM 指令）：见《GM 指令使用说明》第八章 —— GM 命令从定位器取业务服务，是最常见的组合形态。
可运行的示例：`Assets/Revolution.Demo/RevServiceLocator.Demo/`（按钮 A~D 就是"一行注册 / 直接取 / 注销 / 看谁占着内存"）。

## 〇、它是干什么的（一句话）

**把"我用到的某个能力"和"这个能力具体由谁实现"分开。**

```csharp
// 不用它：底层框架想播声音，就得认识上层的声音类 —— 程序集依赖只能单向，写不通
SoundManager.GetInstance().Play("Play_Box_Appear");        // ✗ 底层反向依赖上层

// 用它：底层只认接口，实现"注册"进来，用的时候一行取出来
RevServices.Register<ISoundService, SoundService>();                       // 注册（一行）
RevServices.GetRequired<ISoundService>().Play("Play_Box_Appear");          // ✓ 取用（一行）：谁实现都行，能换、能假、能测
RevServices.Unregister<ISoundService>();                                   // 不用了就注销（释放内存）
```

### 两套写法，怎么选（一句话版）

| | **`RevServices`（推荐，90% 场景）** | `RevServiceLocator.Create()…Build()`（进阶） |
|---|---|---|
| 怎么用 | `Register` / `GetRequired` / `Unregister` 三个静态方法，**不用写静态类、不用链式、不用缓存字段** | 先链式装配再 `Build()` 冻结，自己缓存容器 |
| 能不能注销 | ✅ 随时注销，容器创建的服务会被 `Dispose`，**不长期占内存** | ❌ 装配冻结后不能改，只能整个容器 `Dispose` |
| 作用域（每局一份） | ❌ 全局一份 | ✅ `CreateScope()`：同一个服务类型每局 / 每个场景各一份 |
| 适合 | 全局服务（音频 / 配置 / 网络）、跟着模块或场景生灭的服务 | 同时存在多局战斗、单测里另建隔离容器 |

两套**语义一致**（懒创建 / `OnInit` 钩子 / 循环依赖报错 / 谁创建谁释放），可以放心混用。本文先讲 `RevServices`，作用域那套放在第一章末尾的"进阶一"。


**什么时候用**

- 底层模块要调用上层能力（UI 框架要播声音、动作序列要发奖励、资源系统要报日志）；
- 同一个服务类型在不同场景/不同局面需要**各一份**（一局战斗一份战斗上下文）；
- 你想把业务依赖从框架里赶出去，并且**能在不启游戏的情况下跑单测**。

**什么时候别用**

- 只是"少写一个构造参数" —— 那是过度设计，直接传参更清楚；
- 需要自动解析复杂依赖图（那是 DI 容器的活，且与 IL2CPP 热路径相性差）；
- 进程内只有唯一实现的简单工具类 —— 一个 `static class` 更直接。

## 一、3 分钟跑起来（可粘贴）

### 第 1 步：定义你要用的能力（接口）

```csharp
// 放在底层模块里（谁都能引用它，因为它只是一个接口）
public interface ISoundService
{
    void Play(string eventName);
}

public interface IConfigService
{
    string SoundBankPath { get; }
}
```

### 第 2 步：写实现（业务层）

```csharp
public sealed class SoundService : ISoundService
{
    private IConfigService _config;

    // ★ 构造函数里只初始化自己，不要取别的服务（那是 OnInit 的事）
    public SoundService() { }

    public void Play(string eventName) { /* 真的调你的音频系统 */ }
}

// 需要依赖别人时，实现 RevIServiceInit，在 OnInit 里取
public sealed class SoundServiceWithDeps : ISoundService, RevIServiceInit
{
    private IConfigService _config;

    public void OnInit(RevIServiceLocator services)
        => _config = services.GetRequired<IConfigService>();     // ← 这里取依赖

    public void Play(string eventName) { }
}
```

### 第 3 步：一行注册（放在启动入口，或这个服务所属模块的 `Awake` / `OnEnable` 里）

```csharp
// ★ 就是一行：不用写静态类、不用 static readonly 缓存、不用链式调用、不用 Build
RevServices.Register<ISoundService, SoundServiceWithDeps>();        // 接口 → 实现（零反射；第一次被取用时才创建）
RevServices.Register<IConfigService>(Config.Load());                // 已有的对象（注销时容器不会 Dispose 它）
RevServices.Register<IDebugService>(s => new DebugService(          // 需要构造参数：写个工厂（工厂里可以取别的服务）
    s.GetRequired<IConfigService>().DebugLevel));
```

三种写法对应三种来源：**类型对类型**（容器 `new` 它）、**已有实例**（你 `new` 好的）、**工厂**（需要参数 / 要先读配置）。
**重复注册会当场报错**（框架不静默覆盖）：想换实现，先 `Unregister` 再 `Register`。

### 第 4 步：运行期取用（一行，任何地方）

```csharp
RevServices.GetRequired<ISoundService>().Play("Play_Box_Appear");   // 必须有：没注册就报错（并列出已注册的服务）

RevServices.Get<IDebugService>()?.Draw();                           // 可选能力：没有就返回 null
if (RevServices.TryGet<IDebugService>(out var d)) { d.Draw(); }     // 想要 bool：用在 if 里最顺
bool ok = RevServices.IsRegistered<ISoundService>();                // 只问有没有（不会触发创建）
```

### 第 5 步：不用了就注销（释放内存）

```csharp
RevServices.Unregister<ISoundService>();     // 摘表 + 不再被每帧驱动 + 容器创建的实例会 Dispose
```

**随对象销毁的服务，用 `owner` 一行搞定**（和 `RevTimer` / `RevEvent` 一个套路）：

```csharp
public sealed class BattleModule : MonoBehaviour
{
    private void Awake()
    {
        RevServices.Register<ICombatContext, CombatContext>(owner: this);   // 记下"谁注册的"
        RevServices.Register<IDamageCalc, DamageCalc>(owner: this);
    }

    private void OnDestroy()
    {
        RevServices.UnregisterAllOf(this);       // ← 一行：这个对象注册的服务全部注销（逆创建序释放）
    }
}
```

> **为什么必须能注销？** 只能注册、不能注销的容器，服务一注册就一直占着内存（连同它引用的所有对象：贴图、列表、回调……）。
> 战斗模块退出后还留着战斗上下文，就是典型的"长时间占用内存"。**注销 = 把它从表里摘掉，让 GC 有机会回收。**

### 进阶一：每局一份（作用域）与单测隔离 —— Builder 写法

只有两种情况需要它：**同一个服务类型要同时存在多份**（两局战斗并行、每个场景各一份），或**单测里另建一个隔离的容器**。

```csharp
public static class GameServices
{
    // ★ Builder 这套要自己缓存容器：只 Build 一次，放进 static readonly
    public static readonly RevServiceLocator Root = RevServiceLocator.Create()
        .AddSingleton<ISoundService, SoundServiceWithDeps>()          // 全局一份（接口 → 实现，零反射，启动期不创建）
        .AddSingleton<IConfigService>(Config.Load())                  // 已有实例（容器不释放它）
        .AddScoped<ICombatContext, CombatContext>()                   // 每个作用域一份
        .Build();
}

using (var battle = GameServices.Root.CreateScope())
{
    var ctx = battle.GetRequired<ICombatContext>();   // 这一局独有的一份
    battle.Tick(Time.deltaTime);                     // 驱动这一局里实现了 RevITickable 的服务
}   // ← 离开 using：这一局的服务按"逆创建序"释放
```

**没写 `.Build()` 会怎样？** 编译不过 —— `Create()` 返回的是构建器，只有 `Build()` 才给你容器（这样"忘了冻结装配"是编译期问题，不是运行期事故）。
**代价**：装配 `Build()` 之后冻结，没法单独注销某一个服务（只能整个容器 `Dispose`）——这正是 `RevServices` 存在的原因。

**`RevServices`（推荐）**

|---|---|
| 注册"全局一份"的服务 | `RevServices.Register<ISoundService, SoundService>()` |
| 注册一个**已经存在的对象** | `RevServices.Register<IConfigService>(Config.Load())`（注销时不 Dispose 它） |
| 注册一个需要构造参数的服务 | `RevServices.Register<ISoundService>(s => new SoundService(s.GetRequired<IConfigService>().SoundBankPath))` |

| 取一个**可选**的服务 | `RevServices.Get<IDebugService>()?.Draw()` 或 `if (RevServices.TryGet<IDebugService>(out var d)) ...` |

| 把"取服务入口"交给只认接口的底层模块 | `RevServices.Locator`（类型是 `RevIServiceLocator`） |
| **单测里替换实现** | `RevServices.Unregister<IX>(); RevServices.Register<IX>(new FakeX());`，测试结束 `RevServices.UnregisterAll()` |

**Builder 写法（进阶：作用域 / 多实例 / 隔离容器）**

| 我想做的 | 写法 |
|---|---|
| 注册"全局一份"的服务 | `.AddSingleton<ISoundService, SoundService>()` |
| 注册一个**已经存在的对象** | `.AddSingleton<IConfigService>(Config.Load())` |
| 注册一个需要构造参数的服务 | `.AddSingleton<ISoundService>(s => new SoundService(s.GetRequired<IConfigService>().SoundBankPath))` |
| 注册"每局一份"的服务 | `.AddScoped<ICombatContext, CombatContext>()` |

| 取必需 / 可选的服务 | `services.GetRequired<IX>()` / `services.Get<IX>()` / `services.TryGet<IX>(out var x)` |
| 开一局/一个场景的边界 | `using (var scope = services.CreateScope()) { ... }` |
| 每帧驱动服务 | `services.Tick(Time.deltaTime)`（只要服务实现了 `RevITickable`；**这套要自己调**） |
| 释放（退出场景 / 关游戏） | `services.Dispose()`（幂等，重复调用没事） |
| **单测里另建隔离容器** | 另建一个 `RevServiceLocator.Create()...Build()`，注入假实现（不动生产那份） |

## 三、四个核心概念（讲透，别跳）

### 3.1 Singleton：整个应用一份

- **第一次被取用时才创建**（注册时不会创建，所以启动不会因为"装了一堆系统"变慢）；
- `RevServices` 注册的就是 Singleton：**活到你 `Unregister` 它为止**（或进 Play / `UnregisterAll` 时被清掉）；
- Builder 写法里，根容器（`Root`）和它下面的所有作用域**共享同一个实例**，直到根容器 `Dispose()` 才释放。

> 适合：配置、音频、网络、任务系统、日志 —— 那些"全局只有一个才合理"的东西。

### 3.2 Scoped：每个作用域一份（仅 Builder 写法）

> `RevServices` 没有 Scoped —— 它只管"全局一份"；"每局一份"请用 Builder 写法，或者在局开始时 `Register`、局结束时 `Unregister`（同一时刻只有一局的话，后者更简单）。

- 每个 `CreateScope()` 出来的容器**各持一份**（也就是"同一类型多实例"）；
- **第一次被取用时创建**，随作用域 `Dispose()` 释放；
- ★ **在根容器上取 Scoped 服务会直接报错**（这是刻意的：根没有"一轮"的语义，取到全局唯一的一份就是 bug 的起点）。

```csharp
using (var a = Root.CreateScope())
using (var b = Root.CreateScope())
{
    // a 和 b 拿到的 ICombatContext 是两个不同对象 —— 这就是"同类型多实例"
    var ca = a.GetRequired<ICombatContext>();
    var cb = b.GetRequired<ICombatContext>();

    // 而 Singleton 两者是同一个
    ReferenceEquals(a.GetRequired<IClock>(), b.GetRequired<IClock>());   // true
}
```

> 适合：一局战斗、一个场景、一个房间、一次副本 —— "生命周期有明确边界"的东西。

### 3.3 CreateScope：一层的边界，不再嵌套

- 作用域**只能从根容器开**（一层就够）；在作用域上再 `CreateScope()` 会报错并告诉你正确写法；
- 需要"多轮并发"，就开**多个平行作用域**，而不是作用域里套作用域。

> 为什么刻意只做一层：作用域嵌套会让"某个服务到底属于哪一层"变得难以回答 —— 参考实现就是靠"服务表跟着容器实例走，而不是挂在全局静态上"做到一层隔离的，这个尺度刚好。

### 3.4 谁创建谁负责释放

| 来源 | 谁释放 | 说明 |
|---|---|---|
| `RevServices.Register<IX, X>()` / 工厂注册 | **容器** | `Unregister` / `UnregisterAllOf` / `UnregisterAll` 时 `Dispose`（逆创建序：后创建的先放，因为后创建的可能依赖先创建的） |
| `RevServices.Register<IX>(已有实例)` | **你自己** | 注销只把它从表里摘掉，绝不 `Dispose` 它（你把宿主对象传进来，容器不该替你销毁） |
| `.AddSingleton<IX, X>()` / 工厂注册（Builder） | **容器** | 容器 `Dispose()` 时，逆创建序 |
| `.AddScoped<IX, X>()` / 工厂注册（Builder） | **容器** | 作用域 `Dispose()` 时；根 `Dispose()` 会先释放它的所有作用域 |
| `.AddSingleton<IX>(已有实例)`（Builder） | **你自己** | 容器只持有它、绝不 `Dispose` 它 |

### 3.5 注销：什么时候该注销、注销后会发生什么（`RevServices` 独有）

**什么时候该注销**

| 服务的"命" | 怎么管 |
|---|---|
| 整个游戏都要用（音频 / 配置 / 网络） | 启动时注册，**一般不用注销**（进 Play 或回登录时 `UnregisterAll`） |
| 跟着某个模块 / 场景 / 玩法走（战斗上下文、副本数据、活动系统） | 在它的 `Awake` / `OnEnable` 注册，`OnDestroy` / `OnDisable` **注销**（带 `owner: this`，一行 `UnregisterAllOf(this)`） |

**注销一个服务，会发生这四件事**

1. 从服务表里摘掉（之后 `GetRequired` 会明确报错，并告诉你"它曾被注销过"）；
2. 不再被每帧驱动（如果它实现了 `RevITickable`）；
3. 如果是**容器创建的**（`Register<I, T>()` / 工厂）并且实现了 `IDisposable` → 调用它的 `Dispose()`；你自己传进来的实例 → **不碰**；
4. 它占用的内存，在没人再引用它之后由 GC 回收（容器不再持有它）。

> ⚠ **别人手里已经拿到的引用不会变成 `null`**：注销前你写了 `var s = RevServices.GetRequired<ISoundService>();` 并存了起来，注销后这个 `s` 还在，但服务已经被 `Dispose` 了。
> 所以：**不要把取到的服务长期存成字段**（要用就现取，现取只是一次字典查找，几乎没有成本）；一定要缓存的，在注销时同步清掉。

**没注册 / 已注销时取服务，错误信息会告诉你原因**

```text
取不到服务 ISoundService（当前没有注册）。
· 已注册的服务：IConfigService、IDebugService
· ★ 它曾经被 Unregister 注销过 —— 注销后不能再取；如果还要用，请重新 RevServices.Register。
```

> 这一行"★ 它曾经被注销过"是专门为排查加的：否则你会对着"没注册过"的提示，把启动入口翻个遍，却不知道是别处把它注销掉了。

## 四、完整演练：底层要播声音（参考实现的真实动机）

把"底层 UI 框架要播声音，但声音实现在上层"用本框架表达一遍，只用了 3 个文件：

**① 底层（BaseScripts 层，只引用接口）**

```csharp
// 底层模块里：我只知道"有人能播声音"
public interface ISoundService { void Play(string eventName); }

public static class RevSound
{
    public static void PlayUiSound(RevIServiceLocator services, string name)
    {
        // 可选能力：没接声音系统就不播（不是错误）
        services.Get<ISoundService>()?.Play(name);
    }
}
```

**② 上层（实现层，引用底层）**

```csharp
public sealed class WwiseSoundService : ISoundService
{
    public void Play(string eventName) => Wwise.PostEvent(eventName);
}
```

**③ 启动期把它们接上（一行；全局服务建议集中放在启动入口）**

```csharp
RevServices.Register<ISoundService, WwiseSoundService>();
```

**结果是**：底层再也不认识上层；单测里换成 `FakeSoundService`，被测代码一行不改就能跑：

```csharp
[SetUp]    public void Setup()    { RevServices.Register<ISoundService>(new FakeSoundService()); }   // 用假的
[TearDown] public void TearDown() { RevServices.UnregisterAll(); }                                   // 测完清干净，别污染下一个用例
```

> 需要"另建一个完全隔离的容器"（不想动全局那份）时，用进阶写法：`RevServiceLocator.Create().AddSingleton<ISoundService>(new FakeSoundService()).Build()`。

## 五、为什么用服务定位器，而不是依赖注入容器（王者荣耀的工程实践）

> 这一章回答一个高频问题："为什么框架不提供 `[Inject]` 特性和构造注入？是做不了吗？"
> 答案：**做得了，但刻意不做**。这不是本框架的偷懒——百万行、上线多年的《王者荣耀》做了同样的选择，而且是用自己的三套自研机制（而不是任何 DI 框架）实现的。本章把它讲清楚，给你一张利弊对照表，最后告诉你"什么场合 DI 反而是对的"。

### 5.1 先把四个词分清（新手最容易混成一团）

| 概念 | 一句话 | 王者荣耀里有没有 |
|---|---|---|
| **依赖倒置（DIP）** | 底层只认接口，不认实现类 | ✅ 大量存在（接口定义在底层程序集，实现在上层） |
| **控制反转（IoC）** | "实例从哪来"交给组合根/容器决定，使用方不自己 `new` | ✅ 存在 |
| **服务定位器（SL）** | 需要时去"前台"问一句，拿到实现（**本模块就是**） | ✅ 一处显式调用拿一个实现 |
| **依赖注入容器（DI 容器）** | `[Inject]` 特性、构造注入、自动解析依赖图 | ❌ **没有**（Zenject / VContainer / Extenject 均不存在） |

新手最常见的错误是把后两个划等号：**用了服务定位器 ≠ 用了依赖注入**。准确的说法是：**王者用"手动装配的服务定位器"实现了依赖倒置，但刻意没有引入自动注入容器**——这个"刻意"就是本章要讲的核心。

### 5.2 王者的三件套，正好对应本框架的三个能力

（以下为 2026-09 对王者工程源码的实际统计）

| 王者的机制 | 解决什么问题 | 对应 Revolution 的什么 |
|---|---|---|
| **静态委托定位器**：每个跨层能力一个"返回接口"的委托字段 | 底层程序集不能引用上层实现（跨层调用） | `GetRequired<IX>()`：接口定义在底层，实现启动期注册进来 |
| **全局系统注册表**：注册 + 生命周期 + 每帧挂载 | 全局系统的统一管理与驱动 | `AddSingleton<IX, X>()` + `RevITickable` |
| **场景级服务容器**：服务表跟着场景实例走 | 场景级服务隔离：**多场景并存，同一个服务类型各一份** | `CreateScope()` + `AddScoped` |

也就是说：你在本模块里用到的每个能力，都有一个百万行工程的原型在生产环境里验证过。

### 5.3 为什么连王者都没上 DI 容器（五条真实理由）

1. **IL2CPP + 热路径性能红线**：DI 容器的核心动作是**运行时反射构造**（扫 `[Inject]`、解析依赖图、`Activator.CreateInstance`）。战斗逻辑帧只有 15~30fps，热路径上的任何反射都是风险；IL2CPP 下反射还有 AOT 裁剪坑（要长期养 `link.xml`）。
2. **依赖链必须一眼可见**：DI 的依赖藏在构造函数签名和特性里，"这个系统到底依赖谁"要去翻容器配置；服务定位器是**一行一个显式调用**，全局搜索调用点就能画出依赖图——大团队排错时这是生死区别。
3. **排错路径要短**：DI 容器的典型故障（注入时机不对、循环依赖解析失败）报错发生在**容器内部**，新手读不懂；服务定位器的空引用只有两个原因——**忘了注册，或取早了**，一句人话能说明白（本模块的报错文案就是这么设计的）。
4. **存量迁移成本**：百万行代码接 Zenject 意味着全面改造构造函数。三件套已经用最低成本把"分层解耦"这个真问题解决掉了，就没有理由推倒重来。
5. **作用域隔离有更直接的做法**：游戏里常见"多个场景 / 对局并存，同一个服务类型在不同局里是不同实例"的需求。把服务表做成**实例成员**而不是全局静态，问题就解决了——不需要 DI 容器的子容器概念。这正是本模块 `CreateScope()` 的原型。

### 5.4 公平话：DI 容器不是不好，是"不适合游戏运行时"

为了不误导你，DI 容器**真实的好处**也列出来：

- 构造注入把依赖**写死在签名上**——不看方法体就知道这个类依赖谁，且天然不可变；
- 自动解析复杂依赖图，大团队里"谁依赖谁"不用人工编排；
- 测试生态成熟，换 Mock 是标准操作；
- 与"每个对象要一套独立依赖"的场景天然契合（比如每个 AI 宿主各持一份）。

所以判断标准是**场景**，不是先进与否：

| 场景 | 建议 |
|---|---|
| 游戏运行时（尤其移动端 / 小游戏 / 热路径） | **服务定位器**（本模块）：零反射、显式、排错路径短 |
| 编辑器工具链 / 服务端 / 离线工具 | DI 容器随便用（没有热路径与 AOT 问题） |
| "每个实例要一套独立依赖"（AI 宿主、策略对象） | **构造传参**更合适（见同目录专题《依赖注入vs服务定位器》） |
| 只是想少写一个构造参数 | 都别用，直接传参 |

本框架的立场一句话：**框架级的服务装配用服务定位器；对象级的一次性依赖，老实传构造参数。**

### 5.5 利弊对照表

| 维度 | DI 容器（Zenject / VContainer） | 服务定位器（本模块 / 王者三件套） |
|---|---|---|
| 装配方式 | `[Inject]` + 构造注入，自动 | 显式注册（`Register` 一行）+ 显式获取 |
| 依赖链可见性 | 弱（注入点分散在构造函数与特性上） | **强**（一行一个调用，全局可搜） |
| 运行时反射 | 有（VContainer 可用 SourceGen 缓解） | **零**（泛型 `new()` 工厂） |
| IL2CPP / AOT 风险 | 需要维护裁剪保护 | 无此问题 |
| 热路径成本 | 解析有开销 | 字典一次查找 + 一次转换 |
| 排错 | 容器内部报错（新手读不懂） | 空引用 = 忘注册 / 取早了，一句话说明白 |
| 换实现 | 改绑定，零改动 | 改注册那一行，同样零改动 ✅ |
| 单测 | 注入 Mock | 注册假实现（或另建一个隔离容器）✅ |
| 解耦彻底度 | 更彻底（类不认识容器） | 调用方认识定位器（**反模式风险**，靠下面 5.6 的几道护栏压住） |
| 心智负担 | 要懂容器配置 / 生命周期模型 | 只有三个动词：`Register` / `GetRequired` / `Unregister` |

> 注意第七、八行：**"换实现、可单测"这两个常被当成"必须上 DI"的理由，服务定位器都做得到**——因为依赖倒置的关键在"面向接口 + 外部装配"，不在容器本身。

### 5.6 王者的五条"反哲学"，就是本模块的铁律

| 王者明确不做的事 | 本模块怎么把它变成机制 |
|---|---|
| 不在组合根之外乱改注册（否则退化成全局可变状态） | **Builder 写法**：`Build()` 之后**类型上就没有改的方法**。**`RevServices` 写法**：它必须能注销（否则就是在占内存），所以做不到"冻结"，换成四道护栏——重复注册**当场报错**（不静默覆盖）、注册时记录 `owner`（谁注册的一目了然）、`Dump()` 随时审计"现在注册了什么"、注销后再取会提示"它曾被注销过" |
| 不引入 `[Inject]` 特性与反射构造 | 全部走泛型 `new()` 工厂，零反射 |
| 不把场景级服务挂到全局（会破坏多实例） | Builder 的 `Scoped` 服务在根容器上取**直接报错**；`RevServices` 只管全局一份，要"每局一份"请用 Builder |
| 不追求一个万能容器（生命周期不同就分不同容器） | 只做 Singleton / Scoped 两级，作用域不嵌套 |
| 不在热循环里反复取未注册的系统（会触发注册副作用） | `GetRequired` 没注册**当场就炸**，不拖到线上；已创建服务的取用只是一次字典查找（工程外实测 10 万次 0 字节分配） |

> **一个必须说清楚的取舍**：`RevServices` 允许"随时注册、随时注销"，换来的是易用性和"不长期占内存"，付出的代价是——它**不再是只读的**。
> 全局可变状态正是服务定位器最容易被诟病的地方，所以请遵守两条使用纪律：
> ① **全局服务（音频 / 配置 / 网络）集中在启动入口注册**，别散落在各个业务脚本里；
> ② **跟着模块 / 场景走的服务，谁注册谁注销**（带 `owner: this`，`OnDestroy` 里 `UnregisterAllOf(this)`）。
> 守住这两条，"现在注册了什么"永远一眼能查清（`RevServices.Dump()`）。

### 5.7 一句话总结

> **王者体系的哲学：用接口做倒置，用委托做反转，用集中装配做组织，用分级容器做隔离——全部手工、全部显式、全部零反射。它牺牲了自动注入的优雅，换来移动端大工程的性能确定性与排错直观性。**
>
> 本模块是同一哲学的现代化重写：`Register / GetRequired / Unregister` 三个动词把使用成本压到一行，`CreateScope()` 把"场景隔离"泛化成作用域，`Get / GetRequired / TryGet` 把三套近义入口收敛成一套；**纪律从注释进了代码**——Builder 靠冻结，`RevServices` 靠重复注册报错 + owner + `Dump()`。

> 📎 想看"构造注入 vs 服务定位器"的逐行对比、以及"什么场合构造传参反而更好"的完整论证，读同目录专题文档《依赖注入vs服务定位器》。

## 六、最容易白干半天的坑

**通用（两种写法都会踩）**

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | **注册用接口、取用具体类** | `取不到服务 SoundService` | 取的时候也用接口：`GetRequired<ISoundService>()`（报错信息里会提醒你） |
| 2 | **同一个服务注册两处** | `服务 IXxx 已经注册过了（第一次来自 …，这次来自 …）` | 注册点只留一处（框架刻意不做静默覆盖 —— 静默覆盖是参考实现的老毛病之一）；想换实现先 `Unregister` |
| 3 | **两个服务在构造/OnInit 里互相取** | `检测到循环依赖：A → B → A` | 构造函数只初始化自己；用 `OnInit` 取依赖，且别互相取 |

**`RevServices` 专属**

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 4 | **注册了却忘了注销** | 战斗退出后战斗上下文还在内存里；`Dump()` 里一直有它 | 跟着模块走的服务带 `owner: this`，`OnDestroy` 里 `UnregisterAllOf(this)` |
| 5 | **重进场景 / 重开模块时重复注册** | 第二次进来 `已经注册过了` | 这是在提醒你上一次没注销。在 `OnDestroy` / `OnDisable` 里补上注销（不要用"先试着注销一下"去掩盖） |
| 6 | **把取到的服务长期存成字段** | 注销后字段还指着一个已 `Dispose` 的对象，行为诡异 | 要用就现取（`RevServices.GetRequired<IX>()` 只是一次字典查找）；一定要缓存的，注销时同步清掉 |
| 7 | **`owner` 传了值类型 / 传了临时对象** | `UnregisterAllOf(...)` 返回 0，服务没被清掉 | `owner` 传**引用类型**且前后是同一个对象（通常就是 `this`） |
| 8 | **注册了可 Tick 的服务却没人取用** | `OnTick` 一直没被调用 | 服务是**第一次被取用时才创建**，创建后才开始被驱动；需要启动期就激活，注册后立刻 `Get` 一次 |
| 9 | **在 `OnInit` / 工厂里注销自己** | `在 OnInit 过程中被注销了，本次取用作废` | 不要在创建过程中注销自己；需要退出时在别处注销 |

**Builder 写法专属**

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 10 | **在根容器上取 Scoped** | `ICombatContext 是 Scoped…不能在根容器上取` | 先 `CreateScope()`，在作用域里取 |
| 11 | **忘了把 Build 结果缓存起来** | 每次用都重新 Build（会报"已经 Build 过"或白付装配成本） | 缓存到 `static readonly` 字段 |
| 12 | **想"注销一个服务"** | Builder 容器 `Build()` 后冻结，没有单个注销 | 这是 `RevServices` 的能力；或整个容器 `Dispose()` |

## 七、报错信息怎么读（把真实文案抄给你）

| 你会看到 | 它的意思 | 怎么改 |
|---|---|---|
| `取不到服务 IXxx（当前没有注册）。已注册的服务：…` | 没注册，或者名字对不上 | 看"已注册的服务"列表对一下；**注册用接口就要用接口取** |
| `★ 它曾经被 Unregister 注销过 —— 注销后不能再取…` | **别处把它注销了**（不是"忘了注册"） | 用 `RevServices.Dump()` 看现状；查谁调了 `Unregister<IXxx>()` / `UnregisterAllOf(...)`；还要用就重新 `Register` |
| `IXxx 是 Scoped（每个作用域一份）服务，不能在根容器上取。请在它所属的边界里开作用域…` | 用法错误（不是"没有"）（Builder 写法） | `using (var scope = Root.CreateScope()) { scope.GetRequired<IXxx>(); }` |
| `检测到循环依赖：A → B → A` | 两个服务互相等对方先创建 | 把互相取用挪到 `OnInit` 之后，或改成"只取真正需要的那一个" |
| `服务 IXxx 已经注册过了（第一次来自 …，这次来自 …）` | 重复注册 | 合并到一处；或上一次没注销（`OnDestroy` 里补 `Unregister`）；想换实现先 `Unregister` |
| `服务 IXxx 在创建过程中 / 在 OnInit 过程中被注销了，本次取用作废` | 工厂或 `OnInit` 里把自己注销了 | 不要在创建过程中注销自己 |
| `注销服务时有一个或多个 Dispose 抛出异常（其余服务已正常注销）` | 某个服务的 `Dispose` 抛了错（`AggregateException`） | 看内部异常；其余服务已经正常注销、表是干净的 |
| `这个 RevServiceLocator 已经 Dispose 了 —— 容器释放后不能再取服务` | 用了已释放的容器 | 场景卸载前把需要的东西取好；或别在卸载后还持有旧容器 |
| `作用域不再嵌套：请从根容器 CreateScope()` | 在作用域上又开作用域 | 开多个平行作用域 |
| `这个 RevServiceBuilder 已经 Build 过了` | 重复 Build | 只 Build 一次并缓存 |

## 八、怎么验证它在工作（可直接跑的测试思路）

本模块的内核是**纯 C#**（`Facade` / `Implementation` / `Interfaces` 不引用 UnityEngine；只有 `Support` 里的 Unity 钩子引用），所以能放进普通 .NET 工程跑。

**`RevServices`（注册 / 取用 / 注销）的关键断言**——框架交付时已在工程外跑过 55 条断言全部通过，覆盖下面这些（工程内可以用 NUnit 写成用例）：

```csharp
RevServices.Register<ISound, Sound>();
Assert.AreSame(RevServices.GetRequired<ISound>(), RevServices.Get<ISound>());   // ① Singleton：多次取是同一个，只创建 1 次

// ② 重复注册当场报错，并提示"先 Unregister"
Assert.Throws<InvalidOperationException>(() => RevServices.Register<ISound, Sound>());

// ③ 注销 = 摘表 + 容器创建的实例被 Dispose（恰好 1 次，重复注销不会二次 Dispose）
Assert.IsTrue(RevServices.Unregister<ISound>());
Assert.IsFalse(RevServices.Unregister<ISound>());

// ④ 注销后再取：明确报错，且信息里说明"它曾被注销过"
var e = Assert.Throws<InvalidOperationException>(() => RevServices.GetRequired<ISound>());
StringAssert.Contains("曾经被 Unregister", e.Message);

// ⑤ 你自己传进来的实例：注销只摘表，绝不 Dispose
var cfg = new Config();
RevServices.Register<IConfig>(cfg);
RevServices.Unregister<IConfig>();
Assert.AreEqual(0, cfg.DisposeCount);

// ⑥ owner 批量注销：只清这个 owner 的，逆创建序释放；别的 owner 不受影响
// ⑦ 同一个实例注册成两个服务类型：每帧只驱动 1 次；最后一个持有者注销时才 Dispose
// ⑧ OnInit 失败：原始异常抛给调用方，容器创建的实例被 Dispose（不泄漏），注册还在（可重试）
// ⑨ 个别 Dispose 抛错：其余照常释放、表已清空，最后统一抛 AggregateException
// ⑩ 已创建服务的 GetRequired 热路径：10 万次 0 字节分配（5 轮取最小）

// 测试收尾：清干净，别污染下一个用例
RevServices.UnregisterAll();
```

**Builder 写法（作用域）的关键断言**：

```csharp
var root = RevServiceLocator.Create()
    .AddSingleton<IClock, Clock>()
    .AddScoped<ISession, Session>()
    .Build();

// ① 作用域隔离：两个作用域的 Scoped 不是同一个对象
var a = root.CreateScope();
var b = root.CreateScope();
Assert.AreNotSame(a.GetRequired<ISession>(), b.GetRequired<ISession>());

// ② Singleton 共享：根与作用域拿到同一个
Assert.AreSame(root.GetRequired<IClock>(), a.GetRequired<IClock>());

// ③ Scoped 在根上取会抛异常（用法守卫）
Assert.Throws<InvalidOperationException>(() => root.GetRequired<ISession>());

// ④ 逆创建序释放：先创建的会后释放
//    （容器只释放"自己创建的"实例，业务传进来的对象不会被动）

// ⑤ 释放后再取会抛异常，而不是默默给你一个坏对象
a.Dispose();
Assert.Throws<InvalidOperationException>(() => a.GetRequired<ISession>());
```

> 本框架交付时就是靠这类断言验证的：一条 19 连测全部通过（含循环依赖、失败回滚、Tick 只驱动本容器等）。

## 九、一页速查卡（可打印）

**`RevServices`（推荐）**

- 注册（一行）：`RevServices.Register<IX, X>()` / `Register<IX>(实例)` / `Register<IX>(s => new X(...))`；都可加 `owner: this`
- 取用：`GetRequired<IX>()` 必须有 · `Get<IX>()` 可能有（null） · `TryGet<IX>(out var x)` 要 bool · `IsRegistered<IX>()` 只问有没有
- 注销（释放内存）：`Unregister<IX>()` · `UnregisterAllOf(this)`（对象销毁时） · `UnregisterAll()`（回登录 / 退出）
- 排查：`Debug.Log(RevServices.Dump())`（谁注册了什么、谁还占着）

**钩子（两套写法通用）**

- `RevIServiceInit.OnInit(services)`：创建后取依赖（构造函数里不要取）
- `RevITickable.OnTick(dt)`：每帧做事（`RevServices` **自动驱动**；Builder 写法要自己调 `services.Tick(dt)`）

**Builder 写法（进阶：作用域 / 单测隔离）**

- `RevServiceLocator.Create()` → 构建器；`.AddSingleton<…>()` / `.AddScoped<…>()` → `.Build()` → 容器（自己缓存）
- `CreateScope()` 一局/一个场景一份 · `Dispose()` 逆序释放（幂等）

**四条铁律**

1. `GetRequired` 用于必需依赖（漏注册当场就炸），`Get` 只用于可选能力；
2. 谁创建谁负责释放：容器创建的（`Register<I, T>()` / 工厂）注销时 `Dispose`，你自己传进来的实例由你释放；
3. 全局服务集中在启动入口注册；跟着模块 / 场景走的服务，**谁注册谁注销**（`owner: this` + `UnregisterAllOf(this)`）；
4. 不要把取到的服务长期存成字段（注销后它会变成已 `Dispose` 的对象）。

## 十、与参考实现的对照（简表）

| 保留（精华） | 改掉（糟粕） |
|---|---|
| 显式注册 + 注册点集中（Builder 冻结 / `RevServices` 重复注册报错 + `owner` + `Dump()`） | 202 个 `public static` 可变字段（谁都能改，只靠口头纪律） |
| 接口优先、依赖倒置 | Init 抛异常但实例仍留在容器里（半初始化） |
| 幂等注册 | 重复注册静默覆盖（旧实例还不销毁） |
| **零反射**泛型 `new()` 工厂 | 手写 22 分支 switch 工厂 + 枚举扩展仪式 |
| "先入表、再 Init" 不变量 | 全量卸载不摘钩子（与单个卸载不对称） |
| 能力探测式挂载（`RevITickable` 自动进 Tick 列表） | 内部集合外泄（`GetSystems()` 返回可变 List） |
| 逆序卸载 | 未注入返回 null 兜底 → 掩盖错误，调用点常不判空 |
