〇它是干什么的（一句话）

把「我用到的某个能力」和「这个能力具体由谁实现」分开。

✗ 不用它：底层反向依赖上层
// 底层框架想播声音，就得认识上层的声音类
SoundManager.GetInstance().Play("Play_Box_Appear");
// 但程序集依赖只能单向（上层 → 底层），写不通
✓ 用它：底层只认接口
// 注册（一行）→ 取用（一行）→ 不用了注销（一行）
RevServices.Register<ISoundService, SoundService>();
RevServices.GetRequired<ISoundService>().Play("Play_Box_Appear");
RevServices.Unregister<ISoundService>();   // 释放内存
一句话对照

参考实现用三套机制解决这件事：静态委托定位器（一批"返回接口"的委托字段）+ 全局系统注册表 + 场景级服务容器。 本框架把它收成一套：注册 → 取用 → 注销（外加进阶的作用域）。

两套写法，怎么选（一句话版）

RevServices（推荐，90% 场景）RevServiceLocator.Create()…Build()（进阶）
怎么用Register / GetRequired / Unregister 三个静态方法，不用写静态类、不用链式、不用缓存字段先链式装配再 Build() 冻结，自己缓存容器
能不能注销✅ 随时注销，容器创建的服务会 Dispose，不长期占内存❌ 装配冻结后不能改，只能整个容器 Dispose
作用域（每局一份）❌ 全局一份✅ CreateScope()：同一个服务类型每局 / 每个场景各一份
适合全局服务（音频 / 配置 / 网络）、跟着模块或场景生灭的服务同时存在多局战斗、单测里另建隔离容器

两套语义一致（懒创建 / OnInit 钩子 / 循环依赖报错 / 谁创建谁释放），可以放心混用。本文先讲 RevServices，作用域那套放在第一章末尾的"进阶一"。

什么时候用它 / 别用它

✅ 该用❌ 别用
底层模块要调用上层能力（UI 要播声音、动作序列要发奖励、资源系统要报日志）只是"少写一个构造参数" —— 直接传参更清楚
同一服务类型在不同场景/局面需要各一份（一局战斗一份战斗上下文）需要自动解析复杂依赖图（那是 DI 容器的活，且与 IL2CPP 热路径相性差）
想把业务依赖从框架里赶出去，并且能在不启游戏的情况下跑单测进程内只有唯一实现的简单工具类 —— 一个 static class 更直接

一3 分钟跑起来（可粘贴）

五步：定接口 → 写实现 → 一行注册 → 一行取用 → 不用了一行注销。每局一份的作用域放在最后的"进阶一"。

第 1 步：定义你要用的能力（接口）
放在底层模块里 —— 谁都能引用它，因为它只是一个接口
public interface ISoundService
{
    void Play(string eventName);
}

public interface IConfigService
{
    string SoundBankPath { get; }
}
第 2 步：写实现（业务层）
构造函数里只初始化自己；要依赖别人就实现 RevIServiceInit
// ① 没有依赖的实现
public sealed class SoundService : ISoundService
{
    public void Play(string eventName) { /* 真的调你的音频系统 */ }
}

// ② 需要依赖别人：实现 RevIServiceInit，在 OnInit 里取
public sealed class SoundServiceWithDeps : ISoundService, RevIServiceInit
{
    private IConfigService _config;

    public void OnInit(RevIServiceLocator services)
        => _config = services.GetRequired<IConfigService>();   // ← 这里取依赖

    public void Play(string eventName) { }
}
第 3 步：一行注册
放在启动入口，或这个服务所属模块的 Awake / OnEnable 里 —— 不用静态类、不用缓存字段、不用链式、不用 Build
RevServices.Register<ISoundService, SoundServiceWithDeps>();   // 接口 → 实现（零反射；第一次被取用时才创建）
RevServices.Register<IConfigService>(Config.Load());           // 已有的对象（注销时容器不会 Dispose 它）
RevServices.Register<IDebugService>(s => new DebugService(  // 需要构造参数：写个工厂（工厂里可以取别的服务）
    s.GetRequired<IConfigService>().DebugLevel));
三种写法对应三种来源：类型对类型（容器 new 它）、已有实例（你 new 好的）、工厂（要参数 / 要先读配置）。重复注册会当场报错（框架不静默覆盖）：想换实现，先 Unregister 再 Register。
第 4 步：运行期取用（一行，任何地方）
必需用 GetRequired，可选用 Get / TryGet
RevServices.GetRequired<ISoundService>().Play("Play_Box_Appear");  // 必须有：没注册就报错（并列出已注册的服务）

RevServices.Get<IDebugService>()?.Draw();                         // 可选能力：没有就返回 null
if (RevServices.TryGet<IDebugService>(out var d)) { d.Draw(); }    // 想要 bool：用在 if 里最顺
bool ok = RevServices.IsRegistered<ISoundService>();             // 只问有没有（不会触发创建）
第 5 步：不用了就注销（释放内存）
摘表 + 不再被每帧驱动 + 容器创建的实例会 Dispose
RevServices.Unregister<ISoundService>();

// 随对象销毁的服务，用 owner 一行搞定（和 RevTimer / RevEvent 一个套路）
public sealed class BattleModule : MonoBehaviour
{
    private void Awake()
    {
        RevServices.Register<ICombatContext, CombatContext>(owner: this);   // 记下"谁注册的"
        RevServices.Register<IDamageCalc, DamageCalc>(owner: this);
    }

    private void OnDestroy()
    {
        RevServices.UnregisterAllOf(this);   // ← 一行：这个对象注册的服务全部注销（逆创建序释放）
    }
}
为什么必须能注销？

只能注册、不能注销的容器，服务一注册就一直占着内存（连同它引用的所有对象：贴图、列表、回调……）。战斗模块退出后还留着战斗上下文，就是典型的"长时间占用内存"。注销 = 把它从表里摘掉，让 GC 有机会回收。

进阶一：每局一份（作用域）与单测隔离 —— Builder 写法

只有两种情况需要它：同一个服务类型要同时存在多份（两局战斗并行、每个场景各一份），或单测里另建一个隔离的容器。

public static class GameServices
{
    // ★ Builder 这套要自己缓存容器：只 Build 一次，放进 static readonly
    public static readonly RevServiceLocator Root = RevServiceLocator.Create()
        .AddSingleton<ISoundService, SoundServiceWithDeps>()   // 全局一份（零反射，启动期不创建）
        .AddSingleton<IConfigService>(Config.Load())           // 已有实例（容器不释放它）
        .AddScoped<ICombatContext, CombatContext>()            // 每个作用域一份
        .Build();
}

using (var battle = GameServices.Root.CreateScope())
{
    var ctx = battle.GetRequired<ICombatContext>();   // 这一局独有的一份
    battle.Tick(Time.deltaTime);                     // 驱动这一局里实现了 RevITickable 的服务
}   // ← 离开 using：这一局的服务按"逆创建序"释放
为什么 Builder 要写 .Build()？

不写就编译不过 —— Create() 返回的是"构建器"，只有 Build() 才给你容器，"忘了冻结装配"是编译期问题。 代价：装配 Build() 之后冻结，没法单独注销某一个服务（只能整个容器 Dispose）——这正是 RevServices 存在的原因。

三核心概念（讲透，别跳）

五个概念，理解了就不会用错；3.5 讲"注销"，是 RevServices 独有的。

3.1 Singleton：整个应用一份

  • 第一次被取用时才创建（注册时不会创建，所以不会因为"装了一堆系统"变慢）；
  • RevServices 注册的就是 Singleton：活到你 Unregister 它为止（或进 Play / UnregisterAll 时被清掉）；
  • Builder 写法里，根容器与它下面的所有作用域共享同一个实例，直到根容器 Dispose() 才释放。
适合配置、音频、网络、任务系统、日志 —— 那些"全局只有一个才合理"的东西。

3.2 Scoped：每个作用域一份（仅 Builder 写法）

注意RevServices 没有 Scoped —— 它只管"全局一份"；"每局一份"请用 Builder 写法，或者在局开始时 Register、局结束时 Unregister（同一时刻只有一局的话，后者更简单）。
  • 每个 CreateScope() 出来的容器各持一份（也就是"同一类型多实例"）；
  • 第一次被取用时创建，随作用域 Dispose() 释放；
  • ★ 在根容器上取 Scoped 服务会直接报错 —— 这是刻意的：根没有"一轮"的语义，取到全局唯一的一份就是 bug 的起点。
作用域隔离长什么样 纯 CSS 动画
scope A（第一局）
ICombatContext ← A 自己的一份
ISession ← A 自己的一份
根容器
IClock（Singleton：全局唯一，共享）
IConfig（Singleton：共享）
scope B（第二局）
ICombatContext ← B 自己的一份
ISession ← B 自己的一份

① A 先取 Scoped：容器给 A 创建一份，只属于 A。

② 再取 Singleton：从根容器拿 —— A、B、根拿到的是同一个对象。

③ B 取 Scoped：另建一份，与 A 互不影响（这就是"同类型多实例"）。

对应参考实现：把"服务表跟着场景实例走"做到了极致——同一个服务类型在每个场景里各有一份；本框架把它泛化成 CreateScope()。

3.3 CreateScope：一层的边界，不再嵌套

  • 作用域只能从根容器开（一层就够）；在作用域上再 CreateScope() 会报错并告诉你正确写法；
  • 需要"多轮并发"，就开多个平行作用域，而不是作用域里套作用域。
为什么嵌套会让"某个服务到底属于哪一层"变得难以回答。参考实现用的就是"一层隔离"（服务表跟着容器实例走，不挂全局静态），这个尺度刚好够用。

3.4 谁创建谁负责释放

怎么注册的谁释放说明
RevServices.Register<IX, X>() / 工厂注册容器Unregister / UnregisterAllOf / UnregisterAll 时 Dispose（逆创建序：后创建的先放，因为后创建的可能依赖先创建的）
RevServices.Register<IX>(已有实例)你自己注销只把它从表里摘掉，绝不 Dispose 它（你把宿主对象传进来，容器不该替你销毁）
.AddSingleton<IX, X>() / 工厂注册（Builder）容器容器 Dispose() 时，逆创建序
.AddScoped<IX, X>() / 工厂注册（Builder）容器作用域 Dispose() 时；根 Dispose() 会先释放它下面所有作用域
.AddSingleton<IX>(已有实例)（Builder）你自己容器只持有它、绝不 Dispose 它

3.5 注销：什么时候该注销、注销后会发生什么（RevServices 独有）

服务的"命"怎么管
整个游戏都要用（音频 / 配置 / 网络）启动时注册，一般不用注销（进 Play 或回登录时 UnregisterAll）
跟着某个模块 / 场景走（战斗上下文、副本数据、活动系统）在它的 Awake / OnEnable 注册，OnDestroy / OnDisable 注销（带 owner: this，一行 UnregisterAllOf(this)）

注销一个服务，会发生这四件事：

  1. 从服务表里摘掉（之后 GetRequired 会明确报错，并告诉你"它曾被注销过"）；
  2. 不再被每帧驱动（如果它实现了 RevITickable）；
  3. 如果是容器创建的（Register<I, T>() / 工厂）并且实现了 IDisposable → 调用它的 Dispose()；你自己传进来的实例 → 不碰；
  4. 它占用的内存，在没人再引用它之后由 GC 回收（容器不再持有它）。
别人手里已经拿到的引用不会变成 null

注销前你写了 var s = RevServices.GetRequired<ISoundService>(); 并存了起来，注销后这个 s 还在，但服务已经被 Dispose 了。所以：不要把取到的服务长期存成字段（要用就现取，现取只是一次字典查找，几乎没有成本）；一定要缓存的，在注销时同步清掉。

没注册 / 已注销时取服务，错误信息会告诉你原因：

取不到服务 ISoundService（当前没有注册）。
· 已注册的服务：IConfigService、IDebugService
· ★ 它曾经被 Unregister 注销过 —— 注销后不能再取；如果还要用，请重新 RevServices.Register。
为什么这一行"★ 它曾经被注销过"是专门为排查加的：否则你会对着"没注册过"的提示，把启动入口翻个遍，却不知道是别处把它注销掉了。

四完整演练：底层要播声音（参考实现的真实动机）

三个文件，把"底层要调上层能力"讲清楚。

底层：只认 ISoundService→ 上层：WwiseSoundService 实现它→ 启动入口：一行 Register→ 运行期：GetRequired 到并用
① 底层（BaseScripts 层，只引用接口）
// 底层模块里：我只知道"有人能播声音"
public interface ISoundService { void Play(string eventName); }

public static class RevSound
{
    public static void PlayUiSound(RevIServiceLocator services, string name)
    {
        // 可选能力：没接声音系统就不播（不是错误）
        services.Get<ISoundService>()?.Play(name);
    }
}
② 上层（实现层，引用底层）
public sealed class WwiseSoundService : ISoundService
{
    public void Play(string eventName) => Wwise.PostEvent(eventName);
}
③ 启动期把它们接上（一行；全局服务建议集中放在启动入口）
RevServices.Register<ISoundService, WwiseSoundService>();
结果是：底层再也不认识上层；单测里换 FakeSoundService，被测代码一行不改就能跑。

单测里怎么替换实现

[SetUp]    public void Setup()    { RevServices.Register<ISoundService>(new FakeSoundService()); }   // 用假的
[TearDown] public void TearDown() { RevServices.UnregisterAll(); }                                   // 测完清干净，别污染下一个用例
注意

需要"另建一个完全隔离的容器"（不想动全局那份）时，用进阶写法：RevServiceLocator.Create().AddSingleton<ISoundService>(new FakeSoundService()).Build()。

五为什么用服务定位器，而不是依赖注入容器（王者荣耀的工程实践）

这一章回答一个高频问题："为什么框架不提供 [Inject] 特性和构造注入？是做不了吗？"——答案：做得了，但刻意不做。百万行、上线多年的《王者荣耀》做了同样的选择，而且是用三套自研机制（而不是任何 DI 框架）实现的。

5.1 先把四个词分清（新手最容易混成一团）

概念一句话王者荣耀里有没有
依赖倒置（DIP）底层只认接口，不认实现类✅ 大量存在（接口定义在底层程序集，实现在上层）
控制反转（IoC）"实例从哪来"交给组合根/容器决定，使用方不自己 new✅ 存在
服务定位器（SL）需要时去"前台"问一句，拿到实现（本模块就是）✅ 一处显式调用拿一个实现
依赖注入容器（DI 容器）[Inject] 特性、构造注入、自动解析依赖图❌ 没有（Zenject / VContainer / Extenject 均不存在）
新手最常见的错误 把后两个划等号：用了服务定位器 ≠ 用了依赖注入。准确说法：王者用"手动装配的服务定位器"实现了依赖倒置，但刻意没有引入自动注入容器——这个"刻意"就是本章的核心。

5.2 王者的三件套，正好对应本框架的三个能力

王者的机制解决什么问题对应 Revolution 的什么
静态委托定位器：每个跨层能力一个"返回接口"的委托字段底层程序集不能引用上层实现（跨层调用）GetRequired<IX>()：接口定义在底层，实现启动期注册进来
全局系统注册表：注册 + 生命周期 + 每帧挂载全局系统的统一管理与驱动AddSingleton<IX, X>() + RevITickable
场景级服务容器：服务表跟着场景实例走场景级服务隔离：多场景并存，同一个服务类型各一份CreateScope() + AddScoped

数值为 2026-09 对王者工程源码的实际统计。

5.3 为什么连王者都没上 DI 容器（五条真实理由）

① IL2CPP + 热路径性能红线：DI 容器的核心动作是运行时反射构造（扫 [Inject]、解析依赖图、Activator.CreateInstance）。战斗逻辑帧只有 15~30fps，热路径上任何反射都是风险；IL2CPP 下反射还有 AOT 裁剪坑（要长期养 link.xml）。

② 依赖链必须一眼可见：DI 的依赖藏在构造函数签名和特性里，"这个系统依赖谁"要翻容器配置；服务定位器是一行一个显式调用，全局搜索调用点就能画出依赖图——大团队排错时这是生死区别。

③ 排错路径要短：DI 容器的典型故障报错发生在容器内部，新手读不懂；服务定位器的空引用只有两个原因——忘了注册，或取早了，一句人话能说明白（本模块的报错文案就是这么设计的）。

④ 存量迁移成本：百万行代码接 Zenject 意味着全面改造构造函数。三件套已经用最低成本把"分层解耦"这个真问题解决了，没有理由推倒重来。

⑤ 作用域隔离有更直接的做法：游戏里常见"多个场景 / 对局并存，同一个服务类型在不同局里是不同实例"的需求。把服务表做成实例成员而不是全局静态，问题就解决了——不需要 DI 容器的子容器概念。这正是本模块 CreateScope() 的原型。

5.4 公平话：DI 容器不是不好，是"不适合游戏运行时"

DI 容器真实的好处也要看到：构造注入把依赖写死在签名上（不看方法体就知道依赖谁，天然不可变）；自动解析复杂依赖图，大团队不用人工编排；测试生态成熟；与"每个对象要一套独立依赖"的场景天然契合。

场景建议
游戏运行时（尤其移动端 / 小游戏 / 热路径）服务定位器（本模块）：零反射、显式、排错路径短
编辑器工具链 / 服务端 / 离线工具DI 容器随便用（没有热路径与 AOT 问题）
"每个实例要一套独立依赖"（AI 宿主、策略对象）构造传参更合适（见同目录专题《依赖注入vs服务定位器》）
只是想少写一个构造参数都别用，直接传参
本框架的立场一句话 框架级的服务装配用服务定位器；对象级的一次性依赖，老实传构造参数。

5.6 王者的五条"反哲学"，就是本模块的铁律

王者明确不做的事本模块怎么把它变成机制
不在组合根之外乱改注册（否则退化成全局可变状态）Builder 写法：Build() 之后类型上就没有改的方法。RevServices 写法：它必须能注销（否则就是在占内存），所以做不到"冻结"，换成四道护栏——重复注册当场报错（不静默覆盖）、注册时记录 owner（谁注册的一目了然）、Dump() 随时审计"现在注册了什么"、注销后再取会提示"它曾被注销过"
不引入 [Inject] 特性与反射构造全部走泛型 new() 工厂，零反射
不把场景级服务挂到全局（会破坏多实例）Builder 的 Scoped 服务在根容器上取直接报错；RevServices 只管全局一份，要"每局一份"请用 Builder
不追求一个万能容器（生命周期不同就分不同容器）只做 Singleton / Scoped 两级，作用域不嵌套
不在热循环里反复取未注册的系统（会触发注册副作用）GetRequired 没注册当场就炸，不拖到线上；已创建服务的取用只是一次字典查找（工程外实测 10 万次 0 字节分配）
一个必须说清楚的取舍

RevServices 允许"随时注册、随时注销"，换来的是易用性和"不长期占内存"，付出的代价是——它不再是只读的。全局可变状态正是服务定位器最容易被诟病的地方，所以请遵守两条使用纪律：

① 全局服务（音频 / 配置 / 网络）集中在启动入口注册，别散落在各个业务脚本里；
② 跟着模块 / 场景走的服务，谁注册谁注销（带 owner: this，OnDestroy 里 UnregisterAllOf(this)）。

守住这两条，"现在注册了什么"永远一眼能查清（RevServices.Dump()）。

5.7 一句话总结 王者体系的哲学：用接口做倒置，用委托做反转，用集中装配做组织，用分级容器做隔离——全部手工、全部显式、全部零反射。它牺牲了自动注入的优雅，换来移动端大工程的性能确定性与排错直观性。

本模块是同一哲学的现代化重写：Register / GetRequired / Unregister 三个动词把使用成本压到一行，CreateScope() 把"场景隔离"泛化成作用域，Get / GetRequired / TryGet 把三套近义入口收敛成一套；纪律从注释进了代码——Builder 靠冻结，RevServices 靠重复注册报错 + owner + Dump()。

RevServices.Register<ISound, Sound>();
Assert.AreSame(RevServices.GetRequired<ISound>(), RevServices.Get<ISound>());   // ① Singleton：多次取是同一个，只创建 1 次

// ② 重复注册当场报错，并提示"先 Unregister"
Assert.Throws<InvalidOperationException>(() => RevServices.Register<ISound, Sound>());

// ③ 注销 = 摘表 + 容器创建的实例被 Dispose（恰好 1 次，重复注销不会二次 Dispose）
Assert.IsTrue(RevServices.Unregister<ISound>());
Assert.IsFalse(RevServices.Unregister<ISound>());

// ④ 注销后再取：明确报错，且信息里说明"它曾被注销过"
var e = Assert.Throws<InvalidOperationException>(() => RevServices.GetRequired<ISound>());

// ⑤ 你自己传进来的实例：注销只摘表，绝不 Dispose

RevServices.Unregister<IConfig>();
Assert.AreEqual(0, cfg.DisposeCount);

// ⑥ owner 批量注销：只清这个 owner 的，逆创建序释放；别的 owner 不受影响
// ⑦ 同一个实例注册成两个服务类型：每帧只驱动 1 次；最后一个持有者注销时才 Dispose
// ⑧ OnInit 失败：原始异常抛给调用方，容器创建的实例被 Dispose（不泄漏），注册还在（可重试）

RevServices.UnregisterAll();   // 测试收尾：清干净，别污染下一个用例

Builder 写法（作用域）的关键断言

var root = RevServiceLocator.Create()
    .AddSingleton<IClock, Clock>()
    .AddScoped<ISession, Session>()
    .Build();

// ① 作用域隔离：两个作用域的 Scoped 不是同一个对象
var a = root.CreateScope();
var b = root.CreateScope();
Assert.AreNotSame(a.GetRequired<ISession>(), b.GetRequired<ISession>());

Assert.Throws<InvalidOperationException>(() => root.GetRequired<ISession>());

// ④ 释放后再取会抛异常，而不是默默给你一个坏对象
a.Dispose();
