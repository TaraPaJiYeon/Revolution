〇它是干什么的

先花 30 秒建立直觉，再动手写。

只学 1 件事就能干活（真的） 
RevEvent.AddEventListener(RevAppLifecycle.Resumed, OnResumed, owner: this);   // 回到前台时框架叫你

private void OnResumed() { Reconnect(); RefreshTime(); }

宿主由框架自己建（不显示在 Hierarchy、不用你摆），订阅即生效。

人话 它 = 把 Unity 的"应用级回调"翻译成事件。

你不用认识 OnApplicationPause / OnApplicationFocus，也不用为了收一个"回到前台"去挂 MonoBehaviour。

它替你解决的问题怎么做的
收"前后台"事件要自己挂脚本隐藏宿主自动就位，零配置
切后台时 Pause 与 Focus 一起触发，业务逻辑跑两遍只在"前后台状态真的翻转"时派发一次
不知道这次切出去待了多久（体力 / 活动 / 签到要重算）LastBackgroundSeconds 直接读
排查"怎么老是掉线"PauseCount 计数 + IsBackground 状态
关掉 Domain Reload 后状态残留每次进 Play 自动复位

一3 分钟跑起来（可粘贴）

不用初始化、不用摆物体，订阅即生效。

sealed class ConnectionKeeper : MonoBehaviour
{
    void OnEnable()
    {
        RevEvent.AddEventListener(RevAppLifecycle.Paused,  OnPaused,  owner: this);
        RevEvent.AddEventListener(RevAppLifecycle.Resumed, OnResumed, owner: this);
    }

    void OnDisable() => RevEvent.RemoveAllByOwner(this);      // 一行退订（owner 机制）

    private void OnPaused()
    {
        RevLog.Flush();          // 切后台：把还在队列里的日志落盘（手机随时可能被系统回收）
        SaveLocalState();        // 关键数据"随存随写"，不要攒到退出时再存
    }

    private void OnResumed()
    {
        Reconnect();             // 长连接 / 轮询在后台早断了，这里重连
        RefreshTime();           // 用 LastBackgroundSeconds 决定要不要重算体力 / 活动
    }
}
要点：`owner: this` 一定要传 对象销毁时框架会连同订阅一起摘掉 —— 不必再手写"解绑清单"（这是框架的通用纪律，不止本模块）。

二全部 API（就这些）

门面是静态的，没有实例、没有初始化。

成员类型说明
RevAppLifecycle.Pausedconst string事件名：进入后台 / 失去焦点（0 参数，同一轮只派发一次）
RevAppLifecycle.Resumedconst string事件名：回到前台 / 重新获得焦点
RevAppLifecycle.Quittingconst string事件名：正在退出（不保证触发，见第五节）
RevAppLifecycle.IsBackgroundbool当前是否在后台 / 失焦
RevAppLifecycle.LastBackgroundSecondsfloat最近一次在后台待了多久（秒；从没切过后台为 0）
RevAppLifecycle.PauseCountint累计切后台次数（排查"老是掉线"先看它）
订阅 / 退订全部走 事件系统：RevEvent.AddEventListener(...) / RevEvent.RemoveAllByOwner(this)。 事件名是常量，写错编译期就报错。

三每个事件在什么时候来

一句话：Pause 与 Focus 谁先到都无所谓，框架只认"状态翻转"。

场景会派发什么
手机按 Home、切到别的 App、来电Paused
小游戏切到聊天窗口 / 浏览器切标签页Paused
回到游戏Resumed（此时 LastBackgroundSeconds 是本次时长）
编辑器里点了 Unity 之外的窗口Paused / Resumed —— 故意的，让这条链路在编辑器里就能被测到
主动退出应用Quitting
为什么"切后台"只派发一次 移动端切后台时 Unity 会同时触发 OnApplicationPause(true) 与 OnApplicationFocus(false)： 天真的实现会派发两次 Paused，业务的重连逻辑就跑两遍（甚至两次连接互踩）。 框架只在"前后台状态真的翻转"时派发 —— 谁先到、谁后到都不会漏、也不会重复。

四切后台会带走什么

这才是你需要它的真正原因 —— 三样东西会在你不知情的情况下失效。

被带走的东西表现你该做什么
音频通道被系统打断，回来不响回前台后重播 BGM / 语音（小游戏的音频约束见 RevSoundPlatform）
长连接 / 轮询静默失效 —— 业务以为还连着Resumed 里重连，别等下一次请求超时才反应
时间跨度玩家可能一后台就是半小时用 LastBackgroundSeconds 重算体力 / 活动 / 签到
输入状态抬起事件在切换时丢了（角色一直跑）输入系统已经自己复位了，你什么都不用做
想省事就记一句 Resumed 里做三件事 —— 重连、重播声音、校准时间。
小游戏上这三件事一件都不能省；手机上至少"重连 + 校准时间"要接。

五新手最容易踩的 4 个坑

每一条都对应一个真实故障。

1. 别把关键数据攒到 Quitting 里存 移动端被系统杀掉时什么回调都不会来，Quitting 只在"玩家主动退出"这类场景才触发。 正确做法：数据随存随写；Paused 里再兜一次底。
2. "进游戏就是后台"的情况要兜住 极端情况下（启动瞬间被来电打断），Paused 可能在你的代码订阅之前就派发过了。 需要"此刻状态"时读 RevAppLifecycle.IsBackground，不要只依赖事件。
3. 回调里别做重活、别做同步 IO Paused 给你留的时间很短（系统可能马上冻结进程）—— 这里只适合"标记状态 + 写入很小的数据"。
4. 编辑器里失焦也会派发，这不是 bug 点一下别的窗口再回来，Paused / Resumed 就会各来一次。它是为了让链路可测； 不想要的场景自己判断 Application.isEditor 即可。
